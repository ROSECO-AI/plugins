# Конфигурация и модель данных

Сверено 05.11.2026 с доступной официальной страницей [«Типы элементов»](https://portal.vitrocad.ru/pages/viewpage.action?pageId=23658736) и [примечанием релиза 26.0.2.23](https://portal.vitrocad.ru/pages/viewpage.action?pageId=81298670). Конфигурация конкретного портала может отличаться.

## Базовая модель

Vitro-CAD MP удобно описывать как связку:

- пространство или площадка;
- СХД, где живут папки, документы, версии и связи;
- списки, например "Файлы", "Пользователи", "Роли", "Типы элементов", "Реестр проектов", "Реестр замечаний";
- типы элементов, которые задают набор атрибутов и поведение записей;
- атрибуты, включая lookup на другие списки;
- виды и формы создания;
- права, роли, уникальные разрешения;
- процессы, задачи и автоматизация.

## Типы элементов

Тип элемента определяет набор свойств записи в списке. Дочерний тип элемента наследует атрибуты родительского типа. При проектировании нового типа элемента проверь:

- нужен ли тип для папки;
- какие атрибуты должны отображаться в виде просмотра и форме создания;
- какие поля обязательны;
- какие поля только для чтения;
- какие изменения нужно показывать в активности;
- есть ли вычисления на вкладке "Вычисления";
- в каких списках тип можно создавать через "Ключевые слова".

## Атрибуты и lookup

Для проектных сценариев не смешивай человекочитаемые названия и системные имена. В API и формулах обычно нужны internalName/system name. Для lookup-значений в API передавай идентификаторы элементов, а для множественных lookup - массив идентификаторов.

Типовые системные имена из справки:

- `project_scope_folder` - lookup на папку проекта в карточке проекта.
- `project_scope` - карточка проекта, часто нужна на процессе/задаче для ролевых прав.

В релизе 26.0.2.23 атрибут `project_scope` снят с верхнеуровневого типа «Элемент» и добавлен к типу «Проект»; для других типов требуется отдельная настройка. Перед использованием в процессе или задаче проверь фактическую схему их типов на площадке.

## Ролевое назначение прав

Ролевая модель нужна, когда исполнители и права зависят от проекта.

Минимальная схема:

1. Есть список "Реестр проектов" или аналог.
2. Тип элемента "Карточка проекта" содержит lookup "Папка проекта" с системным именем `project_scope_folder`.
3. В карточке проекта есть lookup-атрибуты участников ролей, например "ГИП", "Архитектор".
4. В списке "Пользователи" -> "Роли" создана отдельная роль для каждого ролевого атрибута.
5. У роли заполнен атрибут с участниками роли, указывающий на соответствующий атрибут карточки проекта.
6. На узлах СХД и в процессах вместо персональных пользователей указываются роли.
7. У типа элемента "Процесс" вычисляется "Карточка проекта" (`project_scope`), например от вложения процесса.
8. У типа элемента "Задача процесса" автоматизация проставляет "Карточка проекта" из процесса.

Практическая проверка: если роль не раскрывается в исполнителей или права не применяются, ищи разрыв в цепочке "папка проекта -> карточка проекта -> project_scope -> роль -> участник роли".

## Реестр замечаний

Замечание является задачей на исправление документации и связано с файлом или папкой. Замечания могут создаваться:

- напрямую в реестре замечаний;
- на элементе файла в СХД;
- во вложениях задачи;
- через маркап в просмотрщике файлов или 3D-модели.

В ответах по замечаниям учитывай три зоны интерфейса реестра: дерево СХД, таблица замечаний, правая панель с информацией/активностью/связями.
