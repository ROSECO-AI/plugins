# REST API Vitro-CAD MP: практическая справка

Проверено 05.11.2026 по доступным официальным материалам и read-only вызову одной корпоративной инсталляции. Разделы справки Confluence частично требуют входа, поэтому это **не полная спецификация текущего релиза**. Перед записью агент должен прочитать тип элемента и текущие данные на самом портале. Назначение методов записи и удаления подтверждено [руководством администратора](https://vitrocad.ru/images/documents/Vitro-MP-%D0%A0%D1%83%D0%BA%D0%BE%D0%B2%D0%BE%D0%B4%D1%81%D1%82%D0%B2%D0%BE-%D0%B0%D0%B4%D0%BC%D0%B8%D0%BD%D0%B8%D1%81%D1%82%D1%80%D0%B0%D1%82%D0%BE%D1%80%D0%B0.pdf) (раздел REST API, версия описания 24.1.37); схема входа дополнительно сверена с [доступным индексированным описанием Login](https://portal.vitrocad.ru/pages/viewpage.action?pageId=105185465). Номер версии корпоративной инсталляции этим не установлен.

## Базовая схема

- Базовый адрес вводится пользователем при установке: `https://portal.example.org/` (пример, замените адресом своего портала).
- Большинство методов вызывается через `POST`.
- Вход: `POST /api/security/Login` с JSON `{"login":"{login}","password":"{password}"}`. Ответ содержит пользовательскую сессию, `token`, `expires`, `status` и `user.isAdmin`. При `status=2` требуется штатный `TwoFactorLogin`; текущий MCP-сервер останавливается до его настройки.
- В следующих запросах заголовок `Authorization: {token}`. Префикс `Bearer` не добавляется. Токен не показывают агенту и не записывают в Markdown или журналы.
- Права определяются пользовательской сессией и разрешениями на объект. `permissionList` в ответе элемента может содержать `read`, `create`, `download`, `update`, `delete`; наличие этих значений нужно проверять для фактического элемента и операции.

## Методы, используемые плагином

| Операция | Метод | Что передать | Инструмент MCP |
| --- | --- | --- | --- |
| Прочитать элемент | `POST /api/item/get/{itemId}` | GUID элемента | `vitro_get_item` |
| Прочитать прямых потомков | `POST /api/item/getList/{parentId}` | GUID списка или папки | `vitro_get_children`, `vitro_list_projects` |
| Прочитать дерево | `POST /api/item/getRecursive/{parentId}` | GUID папки | `vitro_get_recursive` |
| Прочитать список | `POST /api/list/get/{listId}` | GUID списка | `vitro_get_list_metadata` |
| Прочитать типы и поля списка | `POST /api/contenttype/getByList/{listId}` | GUID списка | `vitro_get_content_types` |
| Создать или изменить элемент | `POST /api/item/update` | `multipart/form-data`, поле `itemListJson` с массивом объектов | `vitro_update_item` |
| Загрузить файл | `POST /api/item/update` | `itemListJson` и бинарное поле `fileList` | `vitro_upload_file` |
| Удалить в корзину | `POST /api/item/delete` | массив объектов с `id` | `vitro_delete_item` |
| Восстановить | `POST /api/item/restore/{itemId}` | GUID элемента | `vitro_restore_item` |
| Скачать текущую версию | `POST /api/file/getbyitemid/{itemId}/{version}` | GUID и номер версии из элемента | `vitro_download_file` |

Предыдущая локальная версия проверялась чтением на одной корпоративной инсталляции. У универсального выпуска результаты на иных порталах не подтверждены. Запись, загрузку, удаление и восстановление в новом портале проверяйте только при наличии конкретной задачи и разрешения пользователя. Таблица выше описывает интерфейс пакета и доступные источники, а не подтверждение всех операций в текущей инсталляции.

## Формат элемента и запись

Ответ `get` обычно содержит `id`, `siteId`, `listId`, `parentId`, `contentTypeId`, `itemPath`, `permissionList` и `fieldValueMap`. Ключи в `fieldValueMap` — системные имена атрибутов. Для записи используйте системные имена, не названия из интерфейса.

`api/item/update` принимает в поле `itemListJson` JSON-массив. Для создания обычно нужны `list_id`, `content_type_id`, `parent_id` и обязательные поля типа элемента. Для изменения — `id`, данные текущего списка/типа/родителя и изменяемые поля. MCP-сервер читает существующий элемент и фиксирует его `listId`, `contentTypeId`, `parentId`; несовпадающие значения отклоняет. Для нового элемента агент сначала читает доступные типы списка.

Значения: одиночный lookup — GUID строкой, множественный lookup — массив GUID, дата — ISO 8601 UTC, число — JSON number, текст — JSON string. Для файла в элементе задают `file: 0`, а первый файл передают в `fileList`. Конкретные обязательные поля и валидаторы зависят от типа элемента и настройки площадки.

## Удаление и права

По официальному руководству первый вызов `api/item/delete` помещает элемент в корзину, повторный может удалить его без восстановления. Плагин сверяет GUID, имя и родителя перед вызовом и ведёт локальный журнал GUID, уже удалённых через него. Перед удалением агент запрашивает подтверждение конкретного элемента. После ошибки записи или удаления нельзя слепо повторять запрос: сначала прочитать актуальное состояние.

Административные операции с уникальными правами и списком «Разрывы прав» также существуют в API, но **не входят в инструменты этого плагина**. Плагин рассчитан на обычные учётные записи и не меняет права пользователей.

## Ошибки

- `401`: сессия недействительна или истекла; сервер заново входит. Изменяющий запрос после `401` автоматически не повторяется.
- `403`: учётной записи не разрешена операция над этим объектом; не заменять её административной.
- `404` или пустой результат: проверить GUID, тип объекта и видимость для пользователя.
- Ошибка валидатора или обязательного поля: прочитать тип элемента и условия; не обходить правило.

При диагностике фиксировать HTTP-код, имя метода, GUID объекта и безопасное описание ответа. Не записывать пароль, токен и полный ответ входа.
