# REST API и обнаружение схемы

## Базовый маршрут

1. Вход: `POST {base_url}/api/security/Login` с JSON `{"login":"...","password":"..."}`.
2. После успешного входа используй `token` в `Authorization` без `Bearer`.
3. Ответ входа обычно содержит `user.item.listId`. Это кандидат на системный список пользователей, но его нужно проверить.
4. Чтение всего списка: `POST {base_url}/api/item/getRecursive/{list_id}`.

Не используй `parentId` текущего пользователя без проверки: он может обозначать подгруппу и дать неполный подсчёт.

## Поля

В проверенной схеме встречались:

- `content_type_id` — lookup типа элемента;
- `principal_active_license_type` — lookup активной лицензии;
- имя lookup — обычно `value.fieldValueMap.name`.

Эти имена не являются гарантией для всех версий. Шаблон сначала ищет точное поле, затем безопасно ищет единственное lookup-поле, в котором встречаются `WEB` или `PRO`. Если кандидатов несколько или нет, нужно остановиться.

## Проверка полноты

Перед первым замером проверь:

- что ответ — JSON-массив;
- что в нём есть тип элемента «Пользователь» или однозначно распознанные записи;
- что число подсчитанных записей не равно нулю;
- что выбрано одно поле активной лицензии;
- что агрегаты не превышают общее число подсчитанных записей.

Не печатай значения других полей для диагностики. Достаточны имена кандидатов, HTTP-код и безопасное описание ошибки.
